# 기술 검증: DComp 공유 아틀라스 렌더러 (실험 브랜치 `exp/dcomp-atlas`)

**작성일:** 2026-10-14
**보관 위치:** master 에는 이 보고서만 둔다(결정 기록). 실험 코드·측정 데이터·재현 도구는 `exp/dcomp-atlas` 브랜치에 있다.
**결론:** 결과가 **명확하게 유리하지 않다.** 승인 조건("명확하게 유리하고 기능 회귀가 없을 때만")에 따라 **ADR-02 변경을 제안하지 않는다.** 기존 D3D11 스왑체인 렌더러를 유지하고, 실험 코드는 이 브랜치에만 남긴다.

**사용자 결정 (2026-10-14):**
- 이 브랜치를 보존하고 master 에 병합하지 않는다.
- 기본 렌더러는 D3D11 스왑체인을 유지한다.
- R4(렌더러 교체)는 당분간 중단한다.
- 다중 캐릭터 최적화나 P5 3D 단계에서 필요하면 다시 검토한다.

**덤으로 얻은 결과:** 검증하다가 **기존 렌더러에도 있던 GPU 재생성 후 펫이 보이지 않는 버그**를 찾았다. 수정은 master 에도 반영한다.

---

## 1. 무엇을 만들었나

- 캐릭터마다 아틀라스를 `IDCompositionSurface` 한 장에 원본 크기로 한 번만 그린다.
  - 그리기는 기존 `SpriteRenderer` 로 하고, 같은 캐릭터 펫끼리 이 surface 를 공유한다.
- 펫 창마다 visual 트리 하나를 둔다.
  - 루트 visual: clip = 창 크기. 이웃 프레임이 보이지 않게 한다.
  - 자식 visual: content = 공유 surface. transform 으로 프레임 선택·좌우 반전·확대를 한다. 보간은 최근접, 가장자리는 HARD.
- 프레임이 바뀌면 transform·clip 만 바꾼다. 모든 펫의 변경을 `IDCompositionDevice::Commit` **한 번**으로 반영한다. D3D 그리기·Present 는 없다.
- hit-test Region 은 그대로 쓴다(`SetWindowRgn`, R1 캐시). 말풍선은 기존 스왑체인을 쓴다.
- 선택 방법: `--renderer=atlas`. 기본값은 `swapchain` 이고, 기존 코드는 바꾸지 않았다.
- 검증용 인자 (실험 브랜치에만 있음):
  - `--pose=frame,flip`: 프레임 고정
  - `--simulate-device-lost=초`: GPU 재생성 경로 강제 실행
  - `tools/dupcap` (Desktop Duplication 캡처)

## 2. 기능 검증 — `tools/measure/atlas_verify.ps1` — **32/32 통과**

방법:
- 단색 배경 창 위 단색 받침 창에 펫을 세운다.
- 두 렌더러의 화면 출력을 Desktop Duplication 으로 캡처해 픽셀 단위로 비교한다.
- 원자료: `logs/exp/20261014_200811_atlas_verify`

| 항목 | 결과 |
|---|---|
| 클리핑 (이웃 프레임 번짐) | 번짐 없음 |
| 좌우 반전 | 일치 |
| 확대 1.0배 · 1.5배 (원본 대비 2배·3배) | 5개 자세 모두 **픽셀 완전 일치** |
| 확대 1.25배 (원본 대비 2.5배, 비정수) | 다른 픽셀 0~2.0%. 최근접 보간에서 반올림 경계(어느 원본 열·행을 한 번 더 반복하나)가 D3D 점 샘플링과 다르다. 눈으로 보면 같다(캡처 확인). 수식상 매핑은 같고 동점 처리만 다르다 |
| hit-test Region | 두 렌더러의 판정이 같다. 어긋남 수가 양쪽 같고, 알파 임계값 경계 픽셀 몇 개다 |
| GPU 재생성 복구 (`--simulate-device-lost`) | 두 렌더러 모두 재생성 후 같은 화면 (수정 후) |

**검증 범위의 한계**
- **DPI 확대:** 이 PC 는 모니터 1대, 100% 배율이다. 그래서 사용자 배율(`[display] scale`)로 같은 확대 경로를 검증했다. 실제 배율이 다른 모니터와 모니터 간 이동은 확인하지 않았다(D10).
- **Device Lost:** 복구 코드 경로를 강제로 실행했다. 드라이버 수준의 실제 장치 제거(TDR)는 승인 전이라 하지 않았다(`dxcap -forcetdr` 미승인).

**발견한 버그 (기존 렌더러 포함)**
- 증상: GPU 재생성 직후 다시 그릴 기상이 없다. 정지한 펫은 다른 이벤트가 올 때까지 빈 창으로 남는다.
  - 커서 근접을 끈 설정에서는 계속 보이지 않았다.
- 수정: 재생성 직후 즉시 다시 그리기 마감(`kDlRedraw`)을 건다.

## 3. 성능 비교 — `tools/measure/renderer_compare.ps1`

조건:
- 같은 캐릭터(`test-orange`), 1·3·5마리 계속 걷기
- 60초 × 3회(안정화 10초), Release, 3회 중앙값
- 원자료: `logs/exp/20261014_201057_renderer`

| 조건 | 앱 CPU (사이클) | 앱 CPU (GetProcessTimes / PDH) | 렌더 단계 | Region | 창 이동 | DWM CPU | DWM GPU | VRAM | 화면 갱신/초 | 갱신 지연 p95 / 최대 |
|---|---|---|---|---|---|---|---|---|---|---|
| 스왑체인 1 | 0.190% | 0.101 / 0.097 | 5.8 | 13.7 | 37.4 | 0.443% | 0.133% | 7.3MB | 8.1 (Present) | 3.7 / 17.6ms |
| 아틀라스 1 | 0.181% | 0.178 / 0.179 | 2.7 | 14.8 | 42.0 | 0.664% | 0.133% | 11.3MB | 8.1 (Commit) | 4.7 / 28.0ms |
| 스왑체인 3 | 0.421% | 0.384 / 0.371 | 12.9 | 44.0 | 69.3 | 0.733% | 0.220% | 7.5MB | 24.2 | 14.5 / 25.7ms |
| 아틀라스 3 | 0.282% | 0.242 / 0.248 | 3.0 | 36.2 | 60.9 | 0.800% | 0.214% | 11.3MB | 8.2 | 7.3 / 26.8ms |
| 스왑체인 5 | 0.646% | 0.310 / 0.300 | 21.9 | 76.7 | 97.2 | 0.872% | 0.310% | 7.8MB | 40.3 | 0.9 / 28.9ms |
| 아틀라스 5 | 0.343% | 0.263 / 0.256 | 3.1 | 48.1 | 69.7 | 0.702% | 0.301% | 11.3MB | 8.3 | 8.4 / 25.6ms |

표 읽는 법:
- 단계별 열(렌더 단계·Region·창 이동)의 단위는 UI 스레드 백만 사이클/초(M1 계측)다.
- DWM 값은 `p0-counters` 의 PDH 값이다(dwm.exe CPU, GPU 엔진 사용률).
- 갱신 지연은 예정된 애니메이션 프레임 전환 시각보다 화면 갱신 호출이 늦은 정도다. 앱 쪽에서 잰 값이며 DWM 표시 시각은 아니다.

회차별 편차 (같은 조건 3회):

| 조건 | 앱 사이클 | DWM CPU |
|---|---|---|
| 스왑체인 1 | 0.18~0.23% | 0.39~0.50% |
| 아틀라스 1 | 0.15~0.21% | 0.35~0.75% |
| 스왑체인 5 | 0.47~0.68% | 0.78~1.04% |
| 아틀라스 5 | 0.31~0.57% | 0.48~1.18% |

**해석**
- **렌더 단계는 거의 없어진다.** 5마리 기준 21.9 → 3.1 Mcyc/s 다. Present 가 Commit 1회로 묶여 화면 갱신 호출도 마릿수와 관계없이 초당 약 8회가 된다.
- **앱 전체 CPU 는 여러 마리에서만 줄어든다.**
  - 3마리 -33%, 5마리 -47%. 1마리는 차이가 없다(0.190 → 0.181%).
  - 앱 비용의 대부분은 여전히 창 이동과 `SetWindowRgn` 이다(M1 결과와 같음). 렌더러를 바꿔도 이 부분은 그대로 남는다.
- **DWM CPU 는 일관된 이득이 없다.** 1마리에서는 아틀라스가 더 높게 나왔다(0.44 → 0.66%, 다만 회차 편차가 0.35~0.75% 로 크다). 5마리에서는 낮게 나왔다(0.87 → 0.70%). 측정 잡음보다 큰 차이라고 말할 수 없다.
- **VRAM 은 늘어난다.** +3.5~4.0MB 다. DComp 가 surface 를 큰 공유 텍스처 단위로 할당하는 것으로 추정한다 `[검증]`.
- **프레임 안정성은 뚜렷한 차이가 없다.** 최대 지연은 두 렌더러 모두 25~29ms 수준이다.

## 4. 판단

| 기준 | 결과 |
|---|---|
| 기능 회귀 없음 | 거의 충족. 비정수 확대에서만 반올림 경계 차이(최대 2% 픽셀, 눈으로는 같음) |
| 명확하게 유리 | **미충족.** 기본 사용 조건인 1마리에서 앱 CPU 이득이 없다. DWM CPU 는 잡음 범위 안에서 엇갈리고, VRAM 은 +3.5MB 다. 이득은 3마리 이상에서 앱 CPU 에만 있다 |

→ **ADR-02 변경을 제안하지 않는다.** 실험 코드는 `exp/dcomp-atlas` 브랜치에 보존한다.

**다시 검토할 조건**
- 펫을 기본으로 여러 마리 띄우는 구성이 되면 다시 본다.
- 3D(P5)처럼 매 프레임 그리기 비용이 큰 렌더러가 생기면 다시 본다. 그때는 아틀라스 방식이 아니라 공유 visual 구조를 다시 검증해야 한다.

## 5. 같은 측정에서 본 더 큰 개선 여지 (참고)

- 앱 비용의 대부분은 **창 이동**(1마리 약 37Mcyc/s)과 **`SetWindowRgn`** 이다.
- master 에 넣은 `[input] hit_region = "clip"` 비교 옵션은 렌더러 교체보다 효과가 컸다(5마리 0.42 → 0.27%).
  - 동작 단위 합집합 Region 을 동작이 바뀔 때만 설정하는 방식이다.
  - 다만 hit-test 정밀도가 조금 떨어진다(ADR-09 결정 사항).
- 창 이동 비용은 이동 빈도(`display.frame_rate`)나 단일 오버레이 창(P0 E2, ADR-10)으로만 줄일 수 있다.
